# EvalForge 项目范围

## 项目名称

EvalForge｜RAG 与 Agent 评测回归平台

## 项目定位

EvalForge 是面向 RAG 系统与 Agent 工作流的实验管理、自动评测、结果对比和持续回归平台。

平台关注的核心不是单次聊天请求，而是不同数据、Prompt、模型、检索配置和 Agent 工作流版本之间的质量变化。

## 核心闭环

数据集版本
+ Prompt 版本
+ 模型版本
+ RAG 配置版本
+ Agent 工作流版本
→ 创建实验
→ 批量运行
→ 自动评测
→ A/B 对比
→ 失败案例沉淀
→ CI 质量门禁
→ 评测报告

## 必须实现

### 数据与知识库

- 文档上传
- 文档解析
- 文档版本管理
- 切片配置与切片版本
- PostgreSQL 与 pgvector
- Elasticsearch BM25
- 向量召回与词法召回
- RRF 混合融合
- 可插拔重排序
- 原文引用

### 实验与评测

- 测试数据集及不可变版本
- 测试样例和相关文档标注
- Prompt 版本
- 模型配置版本
- RAG 配置版本
- Agent 工作流版本
- 批量实验执行
- Recall@K
- Hit Rate@K
- MRR
- 回答正确性
- 引用一致性
- Agent 工具调用成功率
- 延迟、Token 与成本统计
- 两组配置的配对 A/B 对比

### 可靠性与交付

- Trace
- 请求快照
- 请求回放
- 失败案例库
- 回归测试集
- CI 质量门禁
- JSON、Markdown 和 HTML 评测报告
- Docker Compose
- Prometheus 与 Grafana
- Kubernetes 部署
- Worker 故障恢复
- 故障演练
- README 和演示脚本

## 非目标

第一阶段不实现以下内容：

- 通用聊天产品
- 面向终端用户的知识库门户
- 复杂低代码 Agent 编排器
- 自研大语言模型
- 自研向量数据库
- 自研全文搜索引擎
- 一开始就支持所有模型供应商
- 依赖真实付费模型才能运行的 CI
- 仅通过调用第三方评测平台完成核心能力

## 项目原则

1. Evaluation-first，而不是 Chat-first。
2. 先实现可运行、可测试、可展示的最小闭环。
3. 所有参与实验的配置都必须版本化。
4. 已启动的实验必须绑定不可变配置快照。
5. 历史实验必须能够解释和尽可能复现。
6. 核心指标、实验模型、对比逻辑和门禁引擎由项目自行实现。
7. 第三方评测框架只作为插件、兼容层或设计参考。
8. CI 默认使用确定性 Mock，不能依赖付费 API。
9. 先保证正确性和可解释性，再优化吞吐量与部署复杂度。
